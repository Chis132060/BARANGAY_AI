feat(ai): Implement complete RAG Brain Architecture and Multi-Provider Failover System

This commit finalizes the Smart Barangay AI Brain architecture, transforming the platform from a simple keyword-based chatbot into a highly resilient, production-ready AI RAG (Retrieval-Augmented Generation) pipeline. This implementation guarantees that the AI services remain highly available by not relying on any single AI provider.

### Detailed Architectural Overview

#### 1. Multi-Provider AI Failover System
To ensure maximum uptime, we implemented a sophisticated, distributed-systems approach to managing AI API dependencies. We built a unified `AIProviderManager` equipped with built-in circuit breakers, intelligent error classification, configurable failover priority, and normalized responses. 

If the primary AI provider goes down, times out, hits a rate limit, or throws an authentication error, the system will automatically reroute the user's request to the next available healthy provider without the user even noticing.

**Prioritized AI Providers Configured:**
1. **Gemini** (`gemini-3.5-flash`) - *Primary Provider*
2. **Groq** (`llama-3.1-8b-instant`) - *Fallback Provider 1*
3. **OpenRouter** (`meta-llama/llama-3.1-8b-instruct`) - *Fallback Provider 2*
4. **Ollama** (`llama3.1`) - *Fallback Provider 3 (Local/Hosted)*

**Circuit Breaker Pattern:**
We implemented a `CircuitBreaker` class that monitors the health of each API endpoint. If an API fails consecutively beyond the threshold (e.g., 3 times), the circuit trips to an `OPEN` state. This prevents the system from hammering a dead API, giving it a 30-second cooldown period before testing it again in a `HALF-OPEN` state.

**Intelligent Error Classification:**
The system uses an `error_classifier.py` to differentiate between unrecoverable client errors (like a bad prompt triggering a content safety filter) and recoverable upstream errors (like a 429 Rate Limit, a 503 Gateway Timeout, or a 401 Auth Error). Only recoverable errors trigger the automatic failover, preventing infinite loops on bad requests.

#### 2. Vector Database Infrastructure
We integrated Supabase and the PostgreSQL `pgvector` extension to handle the semantic retrieval of barangay documents. 
- We upgraded the table schema from accepting 768 dimensions to supporting massive 3,072-dimensional arrays, matching the output of Google's absolute latest embedding model (`gemini-embedding-2`).
- We implemented a remote procedure call (`match_knowledge_chunks`) that performs blazing-fast exact nearest-neighbor cosine-similarity searches across the database.

#### 3. Automated Data Ingestion
To populate the AI's "Brain", we built an automated data ingestion pipeline. The system reads raw text files, chunks them using semantic boundaries, converts those chunks into 3,072-dimension vectors, and batch-inserts them into Supabase. It automatically resolves foreign key constraints by validating against the `knowledge_docs` table before pushing chunks.
